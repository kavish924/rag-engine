Kubernetes Services Reference

Core concepts and manifests for exposing a RAG engine's components (retriever API, vector DB, LLM inference server) inside and outside a cluster.

What a Service Does

A Kubernetes Service provides a stable network identity (a fixed DNS name and virtual IP) for a set of Pods, even as individual Pods are created, destroyed, or rescheduled. Pods are ephemeral and get new IPs on every restart; a Service abstracts that away so other components — such as a RAG application's retriever, embedding server, or LLM inference container — can reliably reach each other by name instead of tracking Pod IPs.

Service Types

TypeBehaviorTypical Use in a RAG Stack
ClusterIPDefault. Internal-only virtual IP, reachable only inside the cluster.Vector DB (Chroma/Milvus), internal embedding service, MLflow tracking server
NodePortExposes the service on a static port on every node's IP.Quick local/dev access to the retriever API without an ingress controller
LoadBalancerProvisions an external cloud load balancer (on supported cloud providers).Public-facing RAG API endpoint in production on AWS/GCP/Azure
ExternalNameMaps a Service to an external DNS name, no proxying.Referencing an external hosted LLM API or managed vector DB from inside the cluster
Headless (clusterIP: None)No virtual IP; DNS returns Pod IPs directly.StatefulSets like a sharded/clustered vector database

Example: ClusterIP Service for a Retriever API

manifest

retriever-service.yaml

Exposes a FastAPI-based retriever/embedding service internally to other Pods (e.g. an orchestration/agent layer built with LangGraph).

apiVersion: v1
kind: Service
metadata:
  name: retriever-service
spec:
  selector:
    app: retriever
  ports:
    - protocol: TCP
      port: 8000
      targetPort: 8000
  type: ClusterIP

Example: LoadBalancer Service for a Public RAG API

manifest

rag-api-service.yaml

apiVersion: v1
kind: Service
metadata:
  name: rag-api
spec:
  selector:
    app: rag-api
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
  type: LoadBalancer

Example: Headless Service for a Vector DB StatefulSet

manifest

vector-db-headless.yaml

Used when each vector DB replica/shard needs a stable, individually addressable DNS entry rather than load-balanced routing.

apiVersion: v1
kind: Service
metadata:
  name: vector-db
spec:
  clusterIP: None
  selector:
    app: vector-db
  ports:
    - port: 8080
      targetPort: 8080

Service Discovery (DNS)

Kubernetes assigns every Service a DNS name in the form <service-name>.<namespace>.svc.cluster.local. Within the same namespace, the short name alone is sufficient. 

# From inside the "rag-orchestrator" Pod, reaching the retriever service:
http://retriever-service:8000/search

# Cross-namespace reference:
http://retriever-service.rag-system.svc.cluster.local:8000/search

Common kubectl Commands for Services

kubectl get services
kubectl describe service retriever-service
kubectl get endpoints retriever-service      # Confirm it has matching Pod IPs
kubectl port-forward svc/retriever-service 8000:8000   # Local access for testing

Troubleshooting Checklist

1.Does kubectl get endpoints <service> return any Pod IPs? If empty, the selector doesn't match Pod labels.
2.Do the Pod labels exactly match spec.selector in the Service manifest?
3.Is the app inside the Pod binding to 0.0.0.0, not 127.0.0.1?
4.Does targetPort match the actual container port?
5.For LoadBalancer type: is the cloud provider's controller provisioning an external IP? Check kubectl get svc -w.
