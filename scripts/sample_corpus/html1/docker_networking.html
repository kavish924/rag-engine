Docker Networking Cheatsheet

Network modes, common commands, and debugging patterns for containerized ML/backend services.

Network Modes

ModeBehaviorTypical Use
bridgeDefault. Isolated internal network, NAT to host.Standalone containers, dev environments
hostContainer shares host's network stack directly.Performance-sensitive services, avoiding NAT overhead
noneNo networking at all.Fully isolated/offline jobs
overlayMulti-host network for Swarm/cluster setups.Multi-node container orchestration
macvlanContainer gets its own MAC/IP on physical network.Legacy apps needing direct LAN presence

Core Commands

list

List networks

docker network ls
inspect

Inspect a network

Shows connected containers, subnet, gateway, driver.

docker network inspect <network-name>
create

Create a custom bridge network

Custom networks give containers DNS resolution by name — unlike the default bridge.

docker network create my-app-network
connect

Attach a running container to a network

docker network connect my-app-network <container-name>
disconnect

Detach a container from a network

docker network disconnect my-app-network <container-name>
run

Run a container on a specific network

docker run -d --name api --network my-app-network my-image
remove

Remove unused networks

docker network prune

Container-to-Container Communication

Using a custom network + service names

On a user-defined bridge network, containers resolve each other by container name via Docker's embedded DNS.

docker network create backend-net

docker run -d --name postgres-db --network backend-net postgres:16
docker run -d --name fastapi-app --network backend-net my-fastapi-image

# Inside fastapi-app, connect using:
# postgresql://user:pass@postgres-db:5432/dbname

docker-compose (auto-networking)

Compose creates a network automatically; services reach each other by service name.

services:
  api:
    build: .
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: example

# Inside 'api' container: connect to host "db", not "localhost"

Host ↔ Container Communication

Port mapping

Expose a container port to the host machine.

docker run -p 8000:8000 my-fastapi-image
# host_port:container_port

Reaching host services from inside a container

On Docker Desktop (Windows/Mac), use the special DNS name instead of localhost.

host.docker.internal

# Example: connecting to a Postgres instance running on your host machine
postgresql://user:pass@host.docker.internal:5432/dbname

Debugging Networking Issues

Check which network a container is on

docker inspect <container> --format='{{json .NetworkSettings.Networks}}'

Test connectivity between containers

docker exec -it <container> ping <other-container-name>
docker exec -it <container> curl http://<other-container-name>:<port>

Check exposed/listening ports inside a container

docker exec -it <container> netstat -tulnp
# or, if netstat isn't installed:
docker exec -it <container> ss -tulnp

"Connection refused" checklist

1.Is the target container actually running? docker ps
2.Are both containers on the same custom network?
3.Is the app inside the container binding to 0.0.0.0, not 127.0.0.1?
4.Is the port actually exposed/published correctly?
5.Firewall or security group blocking the port (cloud VM case)?
For your stack: when your FastAPI backend, MLflow tracking server, and Postgres are all containerized, put them on one custom bridge network (or a single docker-compose file) so they resolve each other by service name. This avoids hardcoding IPs and matches how you'd structure things for the k3d deployment later — Kubernetes Services provide the same "resolve by name" pattern via cluster DNS.
